ЦЕЛЬ

Сделать понятную и масштабируемую архитектуру игры. Код пишет автор проекта;
помощник объясняет, проверяет ошибки и ведёт заметки о задумках.
Ближайшая задача — разобраться с созданием сущностей и добавлением компонентов.
Пулы, сохранение мира и собственный контейнер — следующие возможные этапы.

1. ОСНОВА, КОТОРУЮ ОБСУЖДАЕМ

Entity — сущность, представленная записью ID в реестре.
Component — данные сущности: Position, HitBox, Dimension и другие.
System — логика, обрабатывающая компоненты множества сущностей.
Registry создаёт сущности и предоставляет доступ к хранилищам компонентов.
Storage хранит компоненты и связь каждого компонента с его владельцем.

В текущем учебном варианте реестр хранит EntityID в std::deque<EntityID>.
Создание добавляет новую запись, выдаёт следующий ненулевой номер и возвращает
EntityID&. Компоненты могут хранить ссылку на этот же объект ID.
Для этого параметр метода хранилища, параметр конструктора компонента и его
поле ID должны передавать/хранить ссылки, а не промежуточные копии.

Отдельная оболочка Entity может хранить доступ к реестру и ID. Она нужна,
чтобы игровой код удобно создавал и получал компоненты. Данные компонентов
остаются в хранилищах. Оболочка сама по себе не ускоряет обработку стен.

2. ЛОГИЧЕСКОЕ УДАЛЕНИЕ И ОЧИСТКА ПРИ ЗАГРУЗКЕ

Идея автора: после разрушения объекта реестр записывает 0 в его объект ID.
Все компоненты со ссылкой на этот ID видят 0. Системы пропускают такие записи.
Сами компоненты и ячейки ID пока остаются в памяти.

Пример значений в реестре:
До удаления:              [1, 2, 3, 4, 5]
После удаления:           [1, 0, 3, 4, 0]
После загрузки сохранения:[1, 3, 4]

В сохранение записываются только активные сущности и компоненты.
Очистка происходит при загрузке в новые или заранее очищенные хранилища.
Само сохранение файла не освобождает занятую память.
Цена подхода: неактивные записи занимают память и проверяются при обходе.

Ссылки и адреса памяти в файл не записываются. Записывается числовой ID
владельца. При загрузке сначала восстанавливается реестр, затем компоненты
получают ссылки на соответствующие новые объекты ID.
Числовой ID и индекс ячейки — разные вещи. После уплотнения ID 3 остаётся 3.
Счётчик выдачи новых ID тоже нужно сохранять: после примера следующий ID — 6.

3. СПИСОК СВОБОДНЫХ ЯЧЕЕК

Чтобы повторно использовать память без постоянного поиска нулей, хранить
список свободных индексов — free list. При удалении добавлять индекс в список,
при создании забирать свободный индекс. Количество известно через size().

Пример с индексами от нуля:
Значения ID:      [1, 0, 3, 4, 0]
Свободные места:  [1, 4]
Повторно используем место 1 для новой сущности с ID 6:
Значения ID:      [1, 6, 3, 4, 0]
Свободные места:  [4]

Это повторное использование ячеек. Оно не уменьшает размер контейнера.
Нельзя дважды добавить один и тот же свободный индекс: иначе два создания
могут получить одну ячейку. Нужно различать активное и уже свободное место.

4. ОСНОВНАЯ НОВАЯ ИДЕЯ: ЗОНЫ ПОД ШАБЛОНЫ

Сделать контейнер зон: общая зона сущностей и отдельные зоны под шаблоны.
Например, WallManager запрашивает у реестра/владельца пулов отдельную зону
для стен, созданных по одному шаблону с одинаковым набором компонентов.
В дальнейшем другие шаблоны также смогут запрашивать свои зоны.

Предварительный набросок типа: std::vector<std::deque<EntityID>>.
Такой вложенный контейнер допустим в C++, но конкретный выбор ещё не принят.

В каждой зоне могут быть:
- записи ID;
- список свободных мест;
- описание набора компонентов и правил их начального заполнения;
- сведения о том, где лежат компоненты каждой сущности.

При уничтожении стены её место становится свободным, а комплект компонентов
остаётся для повторного использования. При создании новой стены берётся
свободное место этой зоны, назначается новый ID и сбрасываются все её данные.
Если свободного места нет, зона растёт.

WallManager может предоставлять удобное создание и управление стенами.
Низкоуровневое хранение зон и свободных мест желательно отделить от логики стен,
чтобы тем же механизмом могли пользоваться другие шаблоны.

Полезные термины:
- Шаблон создания / prefab — набор компонентов и исходных значений.
- Пул объектов — хранение и повторное использование ранее выделенных объектов.
- Free list — список доступных ячеек.
- Архетип — группа по одинаковому набору типов компонентов. Группировка только
  ID по названию шаблона сама по себе ещё не задаёт хранение ECS по архетипам.

5. ОТКРЫТЫЕ ВОПРОСЫ И СЛАБЫЕ МЕСТА

5.1. Старые ссылки могут обозначить новую сущность.
Если ячейка ID меняется с 0 на 6, все старые ссылки на неё увидят 6.
Это относится не только к компонентам стены, но и к снарядам, целям ИИ и
другим внешним связям. Одинаковый тип стен не устраняет эту проблему.
Перед повторным использованием такие связи должны быть завершены либо
проверяться на актуальность. Возможный будущий подход — идентификатор с
поколением. Его старое значение должно сохраняться у внешнего владельца:
ссылка на общий изменяемый счётчик поколения не позволит распознать старую связь.

5.2. Сброс всего состояния.
Нужно явно определить, какие поля сбрасываются: положение, размеры, прочность,
состояния повреждений, временные эффекты и другие данные.
Нужна политика для компонентов, добавленных или удалённых во время жизни стены:
вернуть исходный набор, перенести сущность в другую группу или не использовать
её в этом пуле. Решение пока не выбрано.

5.3. ID-зона ещё не является зоной компонентов.
Векторы Position и HitBox могут находиться отдельно и иметь разные индексы.
Свободное место в реестре не сообщает автоматически расположение компонентов.
Нужно определить связь ячейки пула со всем комплектом данных.
Разделение ID на зоны само по себе не гарантирует ускорения обработки компонентов.

5.4. Стабильность адресов на обоих уровнях.
Добавление в конец deque сохраняет ссылки на его существующие элементы.
Перевыделение внешнего vector делает недействительными ссылки на сами deque.
Сохранность ссылок на внутренние ID требует отдельного обоснования поведения
при переносе/копировании внутренних контейнеров; гарантии одного deque недостаточно.
В отдельной проверке GCC 13.3/libstdc++ рост vector<deque<...>> не вызвал
копирования или перемещения внутренних элементов. Это наблюдение для одной
реализации, а не проверка Visual Studio и не общая гарантия выбранной схемы.
Один из вариантов для дальнейшего изучения — отдельно размещённые пулы под
владением unique_ptr. Другой — контейнер пулов со стабильными адресами при
разрешённых операциях. Окончательное устройство зон пока не выбираем.
deque также не обещает один непрерывный участок памяти для всех своих элементов.

5.5. Уникальность ID между зонами.
Если каждая зона начнёт выдавать номера с 1, появятся совпадения.
Варианты: общий счётчик ID либо составной идентификатор зоны и сущности.
Индекс свободного места не следует использовать как новый уникальный номер.

5.6. Ссылочное поле компонента.
EntityID& нельзя перепривязать обычным присваиванием: оно меняет исходный ID.
У структуры со ссылочным полем автоматически создаваемый оператор присваивания
удалён. Поэтому полная перезапись компонента, сдвиги через vector::erase и
перенос к другому владельцу потребуют отдельно продуманного решения.
Изменение обычных полей компонента и копирующее создание компонента возможны.

5.7. Порядок сохранения, загрузки и очистки.
Загружать сначала записи реестра, затем компоненты и внешние связи.
Сохранять активные данные, сведения о шаблоне/зоне, необходимые для их
восстановления, и состояние выдачи новых ID. Свободные списки можно восстановить.
Во время очистки исключить обращения компонентов к уже уничтоженным ID.

6. ПОСЛЕДОВАТЕЛЬНОСТЬ ДЛЯ ДАЛЬНЕЙШЕГО ОБСУЖДЕНИЯ

1. Завершить и проверить простое создание сущности и добавление Position.
2. Описать один конкретный шаблон стены и полный сброс её состояния.
3. Решить, как обнаруживать устаревшие внешние связи при повторном использовании.
4. Отдельно проверить один пул стен со списком свободных мест.
5. После этого выбирать контейнер зон и обобщать его на другие шаблоны.
6. Возвращаться к усложнению после проверки реальной нагрузки и расхода памяти.

Вопрос, с которого продолжить: зона будет хранить только ID или также управлять
соответствующими наборами компонентов? От ответа зависит структура самого пула.

Сверено с сохранёнными локальными исходниками BlackNote. Это планы и

7.1. Собственный универсальный динамический массив.
Автор хочет создать полноценную для своих задач замену std::vector,
чтобы в дальнейшем по возможности пользоваться собственным контейнером.
Это одновременно часть разработки игры и практика управления памятью в C++.
Контейнер должен подходить не только для ECS: int, пользовательские классы,
структуры и другие типы. Каждый отдельный массив однороден по типу T;
смешивать произвольные типы в одном массиве автор не планирует.
Конкретные требования к операциям над T ещё предстоит определить.

7.2. Настраиваемая вложенность и опорные звенья.
Контейнер должен допускать обычный одномерный массив, двумерную структуру
и дальнейшую вложенность без заранее выбранного числа уровней в архитектуре
(фактическая глубина, разумеется, ограничена ресурсами).
Идея автора — массивы внутри массивов, доступные через опорные звенья.
От одного звена могут начинаться несколько динамических массивов.
У массива можно создать зависимые массивы; исходный уровень тогда становится
множеством опорных звеньев. Это не бинарное дерево поиска и не требование
хранить данные исключительно в листьях.
Вложенность и связи должны изменяться во время работы программы, а не только
задаваться типами при компиляции. Одного Array<Array<T>> для полного замысла
недостаточно. Размещение данных при превращении массива в уровень звеньев,
правила доступа, владения и допустимые связи пока не определены.

7.3. Смена владельца без перемещения самих данных.
Автор хочет менять владельца массива/блока, не трогая находящиеся в нём данные.
Передача владения и перестройка связей должны по возможности сохранять
размещение самих объектов. Предполагается изучить и использовать перемещение;
конкретный механизм управления памятью ещё не выбран.
Это требование к смене владельца, а не уже принятое обещание стабильности
адресов при любом росте, удалении или другой операции контейнера.

7.4. Связь контейнера с зонами, пулами и ID.
Идеи разделения пулов и зон из разделов 3–4 сохраняются. Собственный контейнер
рассматривается как возможная основа для них вместо предварительного
vector<deque<EntityID>>. Окончательное устройство не выбрано.
Автор также предположил, что контейнер может помочь сопоставлять числовой ID
с нужной ячейкой после уплотнения. Механизм сопоставления пока не выбран;
таблица индексов и поиск были вариантами помощника, а не решением автора.

7.5. Начало работы и возможная собственная библиотека.
Автор готов начать с простой одномерной либо двумерной версии и постепенно
развивать её параллельно с игрой. Жёсткий порядок реализации не установлен.
Это уточняет прежнее намерение отложить контейнер до более позднего этапа.
Возникла идея, что эта работа может стать основой собственной библиотеки.
Название, состав библиотеки, интерфейс и способ распространения не определены.

7.6. Стены как границы и испытание удаления и шаблонов.
Границы игрового пространства автор хочет сделать стенами, как в старой
программе, а не ограничением координат по краям окна.
Ближайший намеченный опыт — добавить стены в ECS-прототип и на них пробовать
логическое удаление и шаблоны создания. Сами шаблоны, зоны и повторное
использование уже описаны выше и здесь не дублируются.
Логику хитбоксов и столкновений автор намерен писать самостоятельно;
raylib используется прежде всего для ввода и отображения.

7.7. Независимость движения от частоты кадров — позже.
Автор выбрал движение при удержании клавиш через IsKeyDown вместо прежней
идеи одного смещения на новое нажатие. Удержание уже реализовано.
Зависимость скорости от частоты кадров пока сознательно оставлена;
устранить её планируется позже. Конкретный способ ещё не выбран.

7.8. Будущий редактор.
Ранее автор упоминал будущий редактор как причину продумывать удобную связь
систем с реестром и не требовать постоянной ручной передачи реестра из main.
Сам редактор остаётся дальней идеей без описанного интерфейса и объёма работ.
Текущую связь System/MovementSystem с Registry не считать отсутствующей:
она уже реализована; дальнейшие требования редактора пока не сформулированы.

Не добавлены как новые задачи: повторная выдача старых ID, замена удалённой
сущности новой прямо сейчас, удаление отдельного компонента и ограничение
позиции краями окна. Автор не выбрал эти предложения для текущего плана.
Логическое удаление обнулением ID уже записано в разделе 2.

8. УЧЕБНЫЕ ТЕМЫ — ДОПОЛНЕНИЕ ОТ 22.10.2026

8.1. Полноценное изучение <stdexcept> и обработки исключений в C++.
По просьбе автора записано для отдельного последующего изучения.
Повод: проверка входящего ID в конструкторе EntitySystems и знакомство
со std::invalid_argument. Использование примера не означает освоение темы.
Это учебный план, а не требование внедрить исключения во всю игру.

Предлагаемый охват изучения:

  и механизмом языка throw / try / catch.

  производных классов, выбор типа ошибки и получение сообщения через what().
- Создание и выбрасывание исключений, перехват по const-ссылке, порядок
  обработчиков, распространение и повторное выбрасывание исключений.
- Ошибки в конструкторах: незавершённое создание объекта, уничтожение уже
  созданных полей и базовых классов; почему return не отменяет создание.
- Раскрутка стека, RAII и освобождение ресурсов при ошибках.
- noexcept, исключения из деструкторов и условия вызова std::terminate.
- Гарантии безопасности исключений при изменении состояния и работе с памятью,
  особенно для будущего собственного динамического массива.
- Когда применять исключения, а когда возвращаемый результат, nullptr или assert;
  отличие ожидаемого отсутствия компонента от нарушения условий работы объекта.
- Небольшие упражнения и разбор ошибок, затем примеры на реестре и контейнере.

Этот раздел уточняет предыдущие планы. Реализованные части отмечены отдельно.

9.1. Entity как основной интерфейс и основа дальнейшего развития.
Автор хочет работать с одной сущностью через Entity: добавлять компоненты,
подключать системы и вызывать поведение без ручной работы с реестром и ID
во внешнем коде. Обращения к реестру должны оставаться внутри этого интерфейса.
Entity рассматривается как основа для игрока, шаблонов и связи с зонами.
Цель — обособить управление сущностью, сохранив её связь с реестром и
подключёнными к ней механизмами, а не копировать данные компонентов в Entity.

9.2. Время жизни сущности и сохранение её данных в пуле.
По замыслу автора удаление Entity должно логически удалять сущность целиком
и прекращать её поведение. Освобождение памяти при этом не обязательно.
Для стены из шаблона её место и набор компонентов должны оставаться в блоке
стен, ожидая повторного использования. Новая стена получает новую идентичность,
а существующие данные обновляются и сбрасываются вместо постоянного создания
и уничтожения всех объектов компонентов. Это уточнение разделов 2–4.
Связь удаления Entity с реестром пока не реализована. Конкретный API удаления,
правила копирования Entity и защита старых связей при переиспользовании
ещё не определены; не считать деструктор уже готовым механизмом удаления.

9.3. Локальное управление системами — мотив и реализованная часть.
Автор хочет избежать поиска зарегистрированного поведения по ID в общей
коллекции на каждом кадре. Для отдельных объектов выбран локальный менеджер
EntitySystems, связанный с одной сущностью. Общий System остаётся отдельным
вариантом; оба используют общую реализацию поведения из System_Component.h.
На этом этапе автор не хочет вводить массив Entity: объекты создаются явно.

Уже реализовано: Entity хранит EntitySystems обычным полем, передавая ему
EntityID& и Registry& при создании. MovementSystem внутри локального менеджера
создаётся по необходимости в optional. Наличие проверяется напрямую без
FindSystem; проверяются ID, необходимые компоненты и повторное подключение.
Entity предоставляет Component<T>, AddSystem<T>, Draw и UseSystem<T>.
Текущий UseSystem<T> обрабатывает WASD и передаёт два направления; это пока
не универсальный интерфейс для любого поведения. Поиск компонентов внутри
MovementSystem сохраняется. Отдельного измерения ускорения не проводилось.

9.4. Расширение новыми типами без правки внутренних классов.
Одна из главных целей автора — описывать новый компонент или систему так,
чтобы реестр, хранилище и механизмы систем могли работать с ним через общий
механизм без ручного добавления веток выбора типа в нескольких местах.
Требуется согласованное распределение обязанностей, а не перенос такого
повторяющегося кода из одного класса в другой. Способ регистрации типов,
описания требований систем и организации хранилищ ещё не выбран.
Текущие шаблонные методы с if constexpr эту цель полностью не реализуют.

9.5. Контейнер как основа замысла, а не только поздняя оптимизация.
Автор уточнил: полноценные шаблоны, зоны, пулы и задуманное переиспользование
после удаления тесно зависят от собственного контейнера. Простые версии на
текущем хранении не следует выдавать за реализацию всей этой архитектуры.
Автор допускает сделать предварительное удаление или шаблоны с зонами уже
сейчас, чтобы продолжать игру и получить опыт, понимая ограничения прототипа.
Ближайший выбор — удаление либо первый вариант шаблонов с зонами; не считать
весь этот набор обязательным объёмом одного следующего занятия.

9.6. Пересмотр архитектуры после практики.
Нынешний System автор считает первоначальным решением, не рассчитанным на
все будущие задачи. Намерение — продолжать работающую игру, изучать реальные
требования и ограничения, затем при необходимости глубоко переработать её,
вплоть до реализации заново. Это не поручение переписать проект сейчас.
Уход на более низкий уровень, чем C++, упоминался как возможная гипотеза,
а не установленная необходимость или выбранная технология.

9.7. Отложенная отладочная панель.
Вместо постоянного вывода движения в консоль автор хочет позднее отображать
отладочные сведения поверх окна игры, включая и скрывая панель по кнопке,
по аналогии с Minecraft. Это панель средствами рисования raylib, а не уже
готовая встроенная консоль библиотеки. Конкретная кнопка и состав не выбраны.
Панель отложена до более рабочего состояния игры. Постоянные сообщения об
успешном движении уже убраны из MovementSystem; панель ещё не реализована.

9.8. Дополнительные темы обучения.
При создании массива автор хочет отдельно изучить выделение и выравнивание
памяти, создание объектов в подготовленной памяти, время жизни и уничтожение.
Пока для отложенного создания локальной системы принято использование
std::optional; это не решение о будущем внутреннем устройстве массива.
Также автор хочет когда-нибудь изучить сокеты. Это отдельный интерес без
срока и без принятого плана сетевой игры. Тема исключений уже записана в 8.1.
