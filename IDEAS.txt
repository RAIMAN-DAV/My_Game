Дата: 06.09.2026

Статус: черновик обсуждения. Решения ниже ещё не утверждены.
Планируемое место в проекте: IDEAS.txt в корне ветки ecs-draft.

ЦЕЛЬ

Сделать понятную и масштабируемую архитектуру игры. Код пишет автор проекта;
помощник объясняет, проверяет ошибки и ведёт заметки о задумках.
Ближайшая задача — разобраться с созданием сущностей и добавлением компонентов.
Пулы, сохранение мира и собственный контейнер — следующие возможные этапы.

1. ОСНОВА, КОТОРУЮ ОБСУЖДАЕМ

Entity — сущность, представленная записью ID в реестре.
Component — данные сущности: Position, HitBox, Dimension и другие.
System — логика, обрабатывающая компоненты множества сущностей.
Registry создаёт сущности и предоставляет доступ к хранилищам компонентов.
Storage хранит компоненты и связь каждого компонента с его владельцем.

В текущем учебном варианте реестр хранит EntityID в std::deque<EntityID>.
Создание добавляет новую запись, выдаёт следующий ненулевой номер и возвращает
EntityID&. Компоненты могут хранить ссылку на этот же объект ID.
Для этого параметр метода хранилища, параметр конструктора компонента и его
поле ID должны передавать/хранить ссылки, а не промежуточные копии.

Отдельная оболочка Entity может хранить доступ к реестру и ID. Она нужна,
чтобы игровой код удобно создавал и получал компоненты. Данные компонентов
остаются в хранилищах. Оболочка сама по себе не ускоряет обработку стен.

2. ЛОГИЧЕСКОЕ УДАЛЕНИЕ И ОЧИСТКА ПРИ ЗАГРУЗКЕ

Идея автора: после разрушения объекта реестр записывает 0 в его объект ID.
Все компоненты со ссылкой на этот ID видят 0. Системы пропускают такие записи.
Сами компоненты и ячейки ID пока остаются в памяти.

Пример значений в реестре:
До удаления:              [1, 2, 3, 4, 5]
После удаления:           [1, 0, 3, 4, 0]
После загрузки сохранения:[1, 3, 4]

В сохранение записываются только активные сущности и компоненты.
Очистка происходит при загрузке в новые или заранее очищенные хранилища.
Само сохранение файла не освобождает занятую память.
Цена подхода: неактивные записи занимают память и проверяются при обходе.

Ссылки и адреса памяти в файл не записываются. Записывается числовой ID
владельца. При загрузке сначала восстанавливается реестр, затем компоненты
получают ссылки на соответствующие новые объекты ID.
Числовой ID и индекс ячейки — разные вещи. После уплотнения ID 3 остаётся 3.
Счётчик выдачи новых ID тоже нужно сохранять: после примера следующий ID — 6.

3. СПИСОК СВОБОДНЫХ ЯЧЕЕК

Чтобы повторно использовать память без постоянного поиска нулей, хранить
список свободных индексов — free list. При удалении добавлять индекс в список,
при создании забирать свободный индекс. Количество известно через size().

Пример с индексами от нуля:
Значения ID:      [1, 0, 3, 4, 0]
Свободные места:  [1, 4]
Повторно используем место 1 для новой сущности с ID 6:
Значения ID:      [1, 6, 3, 4, 0]
Свободные места:  [4]

Это повторное использование ячеек. Оно не уменьшает размер контейнера.
Нельзя дважды добавить один и тот же свободный индекс: иначе два создания
могут получить одну ячейку. Нужно различать активное и уже свободное место.

4. ОСНОВНАЯ НОВАЯ ИДЕЯ: ЗОНЫ ПОД ШАБЛОНЫ

Сделать контейнер зон: общая зона сущностей и отдельные зоны под шаблоны.
Например, WallManager запрашивает у реестра/владельца пулов отдельную зону
для стен, созданных по одному шаблону с одинаковым набором компонентов.
В дальнейшем другие шаблоны также смогут запрашивать свои зоны.

Предварительный набросок типа: std::vector<std::deque<EntityID>>.
Такой вложенный контейнер допустим в C++, но конкретный выбор ещё не принят.

В каждой зоне могут быть:
- записи ID;
- список свободных мест;
- описание набора компонентов и правил их начального заполнения;
- сведения о том, где лежат компоненты каждой сущности.

При уничтожении стены её место становится свободным, а комплект компонентов
остаётся для повторного использования. При создании новой стены берётся
свободное место этой зоны, назначается новый ID и сбрасываются все её данные.
Если свободного места нет, зона растёт.

WallManager может предоставлять удобное создание и управление стенами.
Низкоуровневое хранение зон и свободных мест желательно отделить от логики стен,
чтобы тем же механизмом могли пользоваться другие шаблоны.

Полезные термины:
- Шаблон создания / prefab — набор компонентов и исходных значений.
- Пул объектов — хранение и повторное использование ранее выделенных объектов.
- Free list — список доступных ячеек.
- Архетип — группа по одинаковому набору типов компонентов. Группировка только
  ID по названию шаблона сама по себе ещё не задаёт хранение ECS по архетипам.

5. ОТКРЫТЫЕ ВОПРОСЫ И СЛАБЫЕ МЕСТА

5.1. Старые ссылки могут обозначить новую сущность.
Если ячейка ID меняется с 0 на 6, все старые ссылки на неё увидят 6.
Это относится не только к компонентам стены, но и к снарядам, целям ИИ и
другим внешним связям. Одинаковый тип стен не устраняет эту проблему.
Перед повторным использованием такие связи должны быть завершены либо
проверяться на актуальность. Возможный будущий подход — идентификатор с
поколением. Его старое значение должно сохраняться у внешнего владельца:
ссылка на общий изменяемый счётчик поколения не позволит распознать старую связь.

5.2. Сброс всего состояния.
Нужно явно определить, какие поля сбрасываются: положение, размеры, прочность,
состояния повреждений, временные эффекты и другие данные.
Нужна политика для компонентов, добавленных или удалённых во время жизни стены:
вернуть исходный набор, перенести сущность в другую группу или не использовать
её в этом пуле. Решение пока не выбрано.

5.3. ID-зона ещё не является зоной компонентов.
Векторы Position и HitBox могут находиться отдельно и иметь разные индексы.
Свободное место в реестре не сообщает автоматически расположение компонентов.
Нужно определить связь ячейки пула со всем комплектом данных.
Разделение ID на зоны само по себе не гарантирует ускорения обработки компонентов.

5.4. Стабильность адресов на обоих уровнях.
Добавление в конец deque сохраняет ссылки на его существующие элементы.
Перевыделение внешнего vector делает недействительными ссылки на сами deque.
Сохранность ссылок на внутренние ID требует отдельного обоснования поведения
при переносе/копировании внутренних контейнеров; гарантии одного deque недостаточно.
В отдельной проверке GCC 13.3/libstdc++ рост vector<deque<...>> не вызвал
копирования или перемещения внутренних элементов. Это наблюдение для одной
реализации, а не проверка Visual Studio и не общая гарантия выбранной схемы.
Один из вариантов для дальнейшего изучения — отдельно размещённые пулы под
владением unique_ptr. Другой — контейнер пулов со стабильными адресами при
разрешённых операциях. Окончательное устройство зон пока не выбираем.
deque также не обещает один непрерывный участок памяти для всех своих элементов.

5.5. Уникальность ID между зонами.
Если каждая зона начнёт выдавать номера с 1, появятся совпадения.
Варианты: общий счётчик ID либо составной идентификатор зоны и сущности.
Индекс свободного места не следует использовать как новый уникальный номер.

5.6. Ссылочное поле компонента.
EntityID& нельзя перепривязать обычным присваиванием: оно меняет исходный ID.
У структуры со ссылочным полем автоматически создаваемый оператор присваивания
удалён. Поэтому полная перезапись компонента, сдвиги через vector::erase и
перенос к другому владельцу потребуют отдельно продуманного решения.
Изменение обычных полей компонента и копирующее создание компонента возможны.

5.7. Порядок сохранения, загрузки и очистки.
Загружать сначала записи реестра, затем компоненты и внешние связи.
Сохранять активные данные, сведения о шаблоне/зоне, необходимые для их
восстановления, и состояние выдачи новых ID. Свободные списки можно восстановить.
Во время очистки исключить обращения компонентов к уже уничтоженным ID.

6. ПОСЛЕДОВАТЕЛЬНОСТЬ ДЛЯ ДАЛЬНЕЙШЕГО ОБСУЖДЕНИЯ

1. Завершить и проверить простое создание сущности и добавление Position.
2. Описать один конкретный шаблон стены и полный сброс её состояния.
3. Решить, как обнаруживать устаревшие внешние связи при повторном использовании.
4. Отдельно проверить один пул стен со списком свободных мест.
5. После этого выбирать контейнер зон и обобщать его на другие шаблоны.
6. Возвращаться к усложнению после проверки реальной нагрузки и расхода памяти.

Вопрос, с которого продолжить: зона будет хранить только ID или также управлять
соответствующими наборами компонентов? От ответа зависит структура самого пула.
